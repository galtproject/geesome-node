# GeeSome Node v0.4.6 — release candidate

## Scope

Prepared from stable `master` at `c0e60626` (promotion PR #1335), compared with
published tag `v0.4.5`. This document is release preparation, not publication or
an assertion that all production release gates have passed.

## Highlights

- Reuse verified frontend artifacts from the Docker image and persistent server
  output. Prepared image assets live outside the mounted publication directory.
- Cache frontend builds by their input SHA-256 in BuildKit, so backend-only layer
  invalidation does not require frontend recompilation. Preserve Yarn availability
  across the frontend Node switch; validate output before publication.
- Preserve safe static-gallery header avatars and layout classes while retaining
  HTML sanitization. Existing immutable galleries must be republished to change.
- Add API discovery, scoped asset uploads, SHA-256 metadata, idempotency, async
  operation resources and asset-batch manifests/compaction for automated clients.
- Extend browser-encrypted chat event/device persistence, queued peer delivery,
  gap repair, encrypted attachments and retention controls; add private-group
  membership snapshots and publishing isolation. This remains an evolving chat
  foundation, not a claim of completed production-secure group messaging.
- Add Docker host-storage retention controls and dependency updates. The frontend
  and geesome-libs references also advance from the prior release.

## Upgrade from v0.4.5

1. Back up PostgreSQL and retain the current deployment/image plus persistent data
   paths. Test the upgrade against a restored database before production rollout.
2. After the release PR is merged into `master`, run `npm run docker-upgrade` from
   the server's clean `master` checkout. It pulls the current branch, builds the
   image, restarts the service and waits for readiness. Do not prune caches first.
3. The first build fills the frontend artifact cache. Later matching builds log
   `Reusing BuildKit frontend cache`; startup uses prepared-image or verified
   server output. Missing/evicted caches rebuild normally. A custom frontend or
   changed build settings intentionally changes its fingerprint.
4. Confirm model sync and all migration chains finish, the API responds, media
   load, and gallery publication works. Check chat/asset paths before enabling
   those new features for users. Readiness timeout alone is not proof of a crash;
   inspect container status and logs before restarting again.

Migration `20260731000000-add-agent-api-metadata.cjs` adds nullable
`storageObjects.sha256`, `userApiKeys.lastUsedAt/scopes`, and
`userAsyncOperations.requestId`, plus the concurrent SHA-256 index. New asset,
chat and private-group tables are created by model sync. The migration integrity
inventory includes the new metadata/index checks. Actual restored-v0.4.5 data
compatibility must be demonstrated by rehearsal, not inferred from model sync.

Rollback: retain the pre-upgrade database backup and image/source revision. Do
not automatically run migration `down`: it drops newly collected metadata.
Application-only rollback has not been rehearsed; restoring the paired backup
and previous deployment is the conservative recovery path if upgrade fails.
