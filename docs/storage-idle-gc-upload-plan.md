## Requirements
User authorized all three recommendations: real quiet-period GC scheduling, cleanup phase timing, and durable local acceptance of uploads during GC. Keep deletion/reference fences. Preserve owner/API-key authorization, destinations, quotas, async receipt polling and unknown-outcome safeguards. No production deployment is requested.

## Workstreams and ownership

Inputs: current fence/retirement contracts; outputs: quiet-period policy and persisted phase timings. Can run in parallel with staging. Do not edit API/content/asyncOperation wiring or lifecycle; expose activity hooks in a separate helper. Completion: no age-only forced GC on healthy disk; retries honor quiet policy; distinguish queue/wait/retirement/GC durations.
2. Durable staging (coordinator): content multipart route, private durable staging service, async worker integration, API contracts, deployment docs. Inputs: existing operation queue/receipt mechanisms; outputs: bounded persisted files + receipts and restart behavior. No user body stored in ephemeral /tmp after acceptance; no automatic replay of imports with unknown side effects. Existing clients poll ordinary operation IDs. Completion: uploads accepted while GC blocks IPFS, retained until proven completion, quota/cancellation/restart covered.
3. Integration/review (coordinator): activity hooks, real Docker PostgreSQL/Kubo tests, API docs/security inventory, rollout instructions and commit/push/PR. Requires 1 and 2. Only coordinator pushes; user owns merges.

## Implementation notes
- Baseline: origin/dev 27fc6898. geesome-test runs older 7aa47b91; no production edits.
- Existing multipart parser spools to OS tmp and returns streams; existing async wrapper is process-local and restart marks operations node-restart. Durable staging must use a separate persisted file and queue checkpoint.
- Scheduler implementation: `cleanupActivity` exports `beginStorageActivity` (idempotent completion), `noteStorageActivity`, and `storageActivitySnapshot` for HTTP/writer integration. Every process starts with a fresh conservative 60-second quiet interval. Current activity is process-local; durable-upload queue entries and persisted cleanup waiting/timing receipts survive restart. Multiple application processes require shared activity aggregation before claiming cluster-wide quiet scheduling.
- Healthy-disk cleanup now requires no queued foreground work (including durable-upload), no active local uploads/writers, and 60 seconds since latest activity. Old receipt age, retry backoff expiration, and explicit retry do not bypass this policy. Quiet state is checked again after exclusive-fence acquisition.
- Optional disk-pressure exception uses explicit `STORAGE_CLEANUP_DATA_PATH` filesystem and `STORAGE_CLEANUP_MIN_FREE_BYTES` (default 5 GiB, valid 1 byte through 1 TiB). Missing mount/configuration/errors do not force GC. Existing storageSpace availability methods measure network copies, not filesystem free bytes, so they cannot establish disk pressure. The path must actually expose the Kubo data filesystem; app overlay free space is insufficient.
- Existing receipt JSON now records waiting, retirement, and native-GC phase attempts/start/end/duration/outcome; failed native GC is distinct from its preparation/stat/verification. Incomplete previous phase records remain identifiable on recovery, and lost fences prevent later telemetry checkpoints.
- Focused scheduler/phase/RPC/resumed-retention validation: `node --import tsx node_modules/.bin/mocha --require ./test/setupQuietLogs.cjs test/cleanupSchedulingUnit.test.ts test/storageRpcUnit.test.ts test/siteRetirementUnit.test.ts --timeout 10000` — 13 passed. Integration fixtures that forced cleanup by age/force must explicitly arrange quiet time under the new policy.
- Durable uploads now reserve bounded capacity in a short PG advisory transaction, receive into a per-job persistent private directory, fsync before staged acceptance, and use the existing shared queue processor. Staged operations remain pollable as inProcess; worker-only pending detection preserves existing clients.
- Confirmed import checkpoints become terminal before deleting originals, closing a reviewed crash window. Startup recovers staged jobs and confirmed imported checkpoints; importing/unknown jobs retain originals without replay. Unknown reservations are protected from generic receipt retention cleanup.
- Independent review caught and corrected stale post-fence foreground checks, sync socket disconnect handling, parent-directory fsync and terminal-checkpoint ordering. Focused initial validation: 42 tests passed with disposable PostgreSQL, including cancellation/authorization/hash failures and GC admission.
- Streaming reservation refinement: Content-Length bounds initial capacity; unknown-length uploads reserve at most 16 MiB and grow under parser backpressure. Reservation release/extension share a PG lock and re-read live state, preventing abort from resurrecting quota. Both deferred-budget abort and ten-parallel-small-file tests pass.
